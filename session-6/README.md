# ERA V5 · Session 6 — a Training Data Execution System

A small but complete data system for V5. It proves **what the run consumed, why it consumed it, what the model learned
from it, and how the run can be reconstructed.** The corpus, tokenizer and model are small (500K tokens, a 3M-parameter
transformer, CPU). The guarantees are the point.

```bash
pip install torch tokenizers numpy pytest
python run_demo.py          # ~100 s on a laptop CPU; regenerates submission_artifacts/
python -m pytest -q tests   # 12 invariant tests
```

The output ends with `evidence written: 13/13 requirements passed`. Everything in `submission_artifacts/` is regenerated by the
command; nothing is hand-written.

| artifact | link |
|---|---|
| execution log | [`submission_artifacts/run.log`](submission_artifacts/run.log) |
| evidence (machine-readable) | [`submission_artifacts/evidence.json`](submission_artifacts/evidence.json) |
| evidence (summary) | [`submission_artifacts/evidence.md`](submission_artifacts/evidence.md) |
| manifests, eval registry, compiled schedule | [`submission_artifacts/manifests/`](submission_artifacts/manifests) |
| consumption / OPUS / learning / token ledgers, replay, audit | [`submission_artifacts/ledgers/`](submission_artifacts/ledgers) |

The `.pt` checkpoint weights (~40 MB each) are regenerated by the command and not committed. Their `.json` records are committed.

## The path, and where each step lives

```
documents  -> tokenized shards -> manifests -> mixture schedule -> packing -> batches -> training
           -> consumption ledger -> learning ledger -> checkpoint -> crash -> resume -> replay -> fork -> audit
```

| stage | code | what it guarantees |
|---|---|---|
| frozen tokenizer | `tdes/data.py: FrozenTokenizer`, `tokenizer.lock.json` | The run refuses to start if the tokenizer file's SHA-256 differs from the lock. Every manifest records it. |
| immutable shards + manifests | `build_shards`, `ShardStore.validate` | One `.npy` per shard plus a manifest: content hash, tokenizer hash, every document's span, split and `never_train` flag. Re-writing a shard with different content raises (the demo tries it, and it is refused). |
| eval/validation firewall | `EvalFirewall` | Val/test shards can never be opened as a training stream. Every candidate is checked against 24,088 13-gram fingerprints of the GSM8K test shard. |
| mixture schedule | `tdes/selection.py: compile_schedule` | Two curriculum stages are compiled into exact per-step lane quotas, blended over a 10-step warmup band at the boundary. Protected floors: indic ≥ 1/8 and reasoning ≥ 1/8 of every batch. The compiled schedule is hashed, and recompiling gives the same hash. |
| packing | `tdes/packing.py` | `concat_chop` for web/Indic text, `greedy_files` (whole files) for code, `sft_structured` for chat. Each produces input ids, labels (−100 on document boundaries, padding and SFT prompts), a document index (block-diagonal causal attention) and positions that restart per segment. A packed sequence is **fully described by its segments**, so it can be rebuilt from the shards alone. |
| OPUS | `Opus`, `Run.build_batch` | It oversamples candidates 1.5×, scores each by the cosine between its output-head gradient and a proxy direction (from validation text, never gradient-bearing), and fills each lane's quota with the best candidates. Others are **rejected** (negative alignment, or deferred twice) or **deferred** (lost on quota pressure; they compete again next step). The **protected floor** keeps Indic and reasoning in even when they score low. Every decision is written to the OPUS ledger. |
| training | `Run.train_step` | Two micro-batches per step, with the loss normalised by **tokens**, not micro-batches (the Session 10 bug avoided). |
| ledgers | `Run._append` | **Consumption:** run, branch, parent, step, checkpoint id, micro-batches, samples with segments (shard, document, token span), loss-mask hash, attention/position policy, lane, stage, tokenizer hash, loader version, OPUS decision id and batch SHA-256. **Learning:** per-sample loss linked to shards and documents, with OPUS score and grad norm. **Tokens:** per-token loss and perplexity at steps 5, 40 and 75. |
| checkpoints | `Run.save` / `Run.load` | Model, optimizer, RNG, every lane cursor, the deferred queue, the OPUS proxy state, and **the ledger offsets**. A checkpoint without a data position is incomplete. |
| crash / resume | `run_demo.py` §5–6 | The run crashes after step 44. Resume loads step 40, moves the 5 events written after the checkpoint into `*.rolled_back.jsonl`, and continues. |
| replay | `tdes/audit.py: replay` | Rebuilds steps 20–30 **from the ledger and the shards only** and compares batch hashes. |
| fork | `Run.load(..., branch=)` | Branch `fork-indic-up` starts from `main@40` with a different stage-2 mixture. Its ledger records the parent explicitly. |
| audit | `tdes/audit.py: audit` | Every consumed span exists inside one document of a **train** shard. No loss-bearing tokens match a benchmark. It also checks planned against actual shares, that every consumed sample has an *accepted* decision, and that every sample has a learning record. It builds a per-shard report card. |

## Three findings the system surfaced by itself

**1. The proxy is biased, exactly as Session 5 warned.** The OPUS direction comes from English web validation text. Mean
OPUS scores by lane:

| lane | mean score |
|---|---|
| web | **+0.079** |
| reasoning | +0.024 |
| Indic | **−0.054** |
| code | **−0.096** |

98 Indic sequences were kept only because of the **protected floor** (`protected_floor_override=true` in the OPUS ledger).
Without it, an English proxy would have starved the Indic lane. The 81 code sequences kept by quota are flagged
`mixture_quota_override`, so a reviewer can see where the plan overruled the selector.

**2. The first version failed mixture compliance, and the evidence caught it.** OPUS originally rejected every
negatively-aligned candidate and let other lanes fill the slots. The actual code share fell below plan, and `mixture_compliance`
reported FAIL. The fix makes the mixture the contract: OPUS chooses *which* candidates fill a lane's quota, never *how many*,
and every overrule is flagged.

**3. Packing costs differ by lane.** Text lanes are 99.7% loss-bearing. The SFT reasoning lane is only **43%** loss-bearing,
because prompts carry no loss. That is correct, and it is why SFT tokens are worth counting separately when sizing a budget.

## Performance (`performance.json`)

| measure | value |
|---|---|
| packing utilization (non-pad positions) | 98.7% |
| loss-bearing positions | 85.5% |
| loader alone (pack + materialise) | ~4.8M loss-bearing tokens/s |
| end to end, including OPUS scoring of 1.5× candidates and training on CPU | ~1,700 loss-bearing tokens/s |

Selection, not training, is the expensive part (28.8 s against 14.1 s). OPUS scores every candidate with a forward pass. At
scale that cost is why OPUS scores batches, not sequences, and amortises the proxy direction across many steps.

## Design decisions

- **Segments, not tensors, are the unit of record.** A sample is stored as `(shard, document, start, end, loss_from)` spans.
  The ledger stays small, and replay needs nothing except the shards.
- **Position resets per segment and attention is block-diagonal**, so packing never lets one document see another (tested).
- **Deferred candidates are part of the checkpoint.** If they were not, a resumed run would see a different candidate
  pool and diverge. That is the kind of hidden state that makes "resume" silently wrong.
- **Determinism**: CPU, `torch.use_deterministic_algorithms(True)`, counter-style cursors, and candidate ids that are
  hashes of their segments. This is why the resumed run is bit-identical to the uninterrupted one.
